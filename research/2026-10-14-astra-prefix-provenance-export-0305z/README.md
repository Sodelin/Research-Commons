This is a source-only draft of the origin-ledger exporter required by the
separate full-external successor. It changes neither the running 3591-module
closure nor the first 319-source provider/adapter target. No exporter import,
test, object authentication or execution has occurred at this cutoff.

The fixed original plan is `ef775a7223500314359a9ed02a87d207b18eacda9cddfa5a8990c5e1a8e43f10`.
The exporter refuses an incomplete, failed or extra canonical receipt prefix.
It compares all selected source fields, source bytes, literal command families,
compiler executable identity, canonical receipt bytes and compiler logs. It
does **not** open compiled objects or assert that their recorded hashes match
current binaries. The later unchanged full-external preparation gate performs
that separate authentication.

Origin attribution is explicit:

- The first 916 records must equal the fixed published source-execution archive.
  Every origin is joined to its unique successful module event in the original
  guarded batch. Referenced baseline guards/logs must also match the frozen
  original packet manifest. A successful component before a stopped or failed
  batch retains that actual outer outcome.
- Subsequent ordinary executions must match an actual guard-bound module
  capture, its literal successful event, exact embedded receipt and both logs.
  The three historically used serial command forms are selected by their
  actual batch ranges. Failed invocations are retained as evidence rather than
  substituted for canonical successful records.
- Eight separately adopted diagnostic successes use fixed repair/adoption and
  successful guard pins. Their exact selected receipt, hash and success event
  must match; diagnostic limits remain literal. No historical cause inference
  is made.
- Batches 042, 057 and 059 retain original outer outcome `UNKNOWN`, null timing,
  null exit and null maxima. Separate pinned zero-compiler recovery receipts,
  full saved-file inventories and canonical module copies are authenticated.
  Their successful readbacks never become invented original guard successes.

The resulting schema matches the documented `PREFIX-PROVENANCE.json` consumer
contract, but its status is **candidate pending owner review, publication and
fixed pin**. No script installs `PREFIX_PROVENANCE_SHA`, creates the new 3661
state, runs a compiler, launches a process, alters old evidence or chooses a new
accepted source. Missing or ambiguous origins cause failure. Historical absent
execution/helper/environment fields remain null; the output never normalizes
earlier default, synchronous or Mathlib-specific compiler options.

After the original closure completes and this draft receives independent
review, the owner may run it once under a separate bounded guard (proposed
512 MiB address space, 180 seconds wall, 120 seconds CPU, 64 MiB output-file cap,
unchanged 4 GiB physical stop and disk/RAM floors). The only output accepted is
a new `evidence/PREFIX-PROVENANCE-vN.json` in this packet. Failed runs and partial
outputs are preserved. Any new historical exception requires a source-preserved
reviewed successor rather than a permissive flag.

This tool assembles and authenticates source/execution evidence; it is not a
proof of Python, the operating system, historical compiler correctness, source
option equivalence, native-code refinement or mathematical completion. An
independent reviewer must assess the semantic origin links before installing a
future fixed provenance pin. Actual provider types, axioms and final Lake
execution remain separate obligations.
